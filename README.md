## 1. 项目一句话定义

这是一个面向学生和学生工作室的、以 Obsidian 本地 Vault 为工作空间的：

> **本地优先、邀请制、端到端加密、支持多设备同步、候选修改审核与可视化冲突协调的知识域同步系统。**

用户始终使用磁盘上的普通文件夹和 Obsidian 工作。系统负责端到端加密、同步、设备信任、团队准入、候选修改、审核、历史、恢复和治理；Obsidian 继续负责编辑、插件生态和内容渲染。

本项目当前首先是一份产品与协议设想，不代表已经实现、完成安全审计或达到生产可用状态。

## 2. 为什么要做

当前目标用户主要是：

- 希望在电脑与手机之间自动同步 Obsidian Vault 的学生；
- 希望积累工作室、社团或课程知识库的小型团队；
- 希望让较多受邀成员共同建设知识库、但不公开全部内容的协作群体；
- 重视本地文件所有权，不愿让服务运营方读取笔记正文和附件的用户。

需要解决的核心问题包括：

1. 个人 Vault 的多设备自动同步；
2. 团队 Vault 的成员准入、候选修改与审核；
3. 离线编辑和跨设备冲突的安全协调；
4. 设备丢失、成员退出和域主恢复；
5. 在服务器无法解密内容的前提下维护版本历史；
6. 保证用户的原始 Markdown、附件和 Vault 相对路径不被同步系统破坏。

## 3. 非目标

P1 不是以下产品：

- 多人实时共同编辑同一篇文档的在线编辑器；
- 飞书知识库的完整替代品；
- GitHub 的简单界面封装；
- 服务器可以读取内容的普通云盘；
- 对匿名访客开放的公开知识站点；
- 能阻止合法成员复制、截图或保留已解密内容的 DRM 系统；
- 负责修复所有 Obsidian 渲染和第三方插件兼容问题的运行时；
- 自动把个人域和团队域保持双向镜像的后台同步器。

未来公开站点应是从某个正式发布版本显式导出的独立静态副本，不属于 E2EE 同步域本身。

- **已冻结**：访谈中已经明确接受，除非发现自相矛盾或安全缺陷，否则作为当前产品约束。
- **建议**：当前推荐方案，但尚未最终冻结为 P1 交付要求。
- **待裁决**：实现前仍需要产品决策或实验数据；每个当前待裁决项必须有 `DP-*` registry ID，否则视为未登记硬停止。

## 5. 顶层信任承诺（已冻结）

### 5.1 本地优先

- Vault 是用户磁盘上的普通文件夹；
- 一个域在一台设备上对应一个独立的本地 Vault 文件夹；
- Obsidian 原生负责在不同 Vault 之间切换；
- 本地编辑先安全写入本地文件，不以服务器成功为保存前提；
- 同步失败、配额耗尽、成员退出或域封存都不能删除用户本地文件；
- 服务端状态不能静默覆盖尚未协调的本地 Working。

### 5.2 端到端加密

- 笔记正文、附件、历史快照、文件名、扩展名、路径结构、内部链接和本地修改时间在离开设备前加密；
- 域根密钥和可恢复明文的秘密材料只能在授权设备产生和使用；
- 服务运营方在协议设计上不能解密域内容；
- 账号密码不能单独恢复任何域；
- 服务端不得生成域根密钥，不得保存可独立还原域根密钥的明文材料；
- 加密之外还必须验证设备签名、内容真实性、状态连续性和回滚攻击。

服务器可以看到的最小元数据包括：

- 不透明的账号、域、成员和设备标识；
- 密文对象标识和密文大小；
- 服务端接收时间和访问日志；
- 域状态序号和加密代际；
- 必要的成员、设备和权限事件；
- 完成配额、排序、路由和滥用防护所需的控制信息。

服务器默认不能看到：

- 原始文件名和目录；
- 文件扩展名与内容类型；
- Markdown 正文和 frontmatter；
- 图片、PDF 和 Canvas 内容；
- 内部链接图；
- 候选修改 Diff；
- 详细治理原因。

### 5.3 诚实的安全边界

E2EE 不能保护：

- 已被恶意软件控制的授权终端；
- 合法成员主动复制、截图或外传的内容；
- 用户主动、显式授权发送给外部 AI 的临时明文；
- 已经下载到成员设备的历史副本；
- 运营方通过恶意客户端更新进行的供应链攻击，除非进一步完成可验证构建、签名更新和独立审计。

上线前不能仅凭这份 README 宣称“已经实现零知识安全”或“已经 GDPR 合规”。

## 6. 域模型（已冻结）

### 6.1 域与 Vault

- 域是同步、加密、成员和历史的基本边界；
- 一个本地 Vault 文件夹只能绑定一个域；
- 一台设备上的不同域必须使用不同文件夹；
- 个人域和团队域都拥有独立 `domain_id`、密钥、历史和恢复材料。

### 6.2 域类型不可原地转换

P1 不允许：

- 个人域原地升级为团队域；
- 团队域原地转换为个人域；
- 同一文件夹同时绑定个人域和团队域。

需要转换使用场景时，只能：

1. 从当前本地文件生成一个新的 Vault 文件夹；
2. 使用新的 `domain_id`、密钥、恢复包和历史；
3. 保留原 Vault，不进行原地覆盖；
4. 不在服务器建立可读的祖先或 Fork 关系。

“基于团队本地 Vault 创建个人域”不能称为 Fork；产品文案使用：

> 基于此设备的本地文件创建个人域。

### 6.3 社区协作不是公开域

P1 的“公共构建仓库”仍然是邀请制团队域，只是可能拥有较多贡献成员和阅览成员。

- 域不可搜索；
- 未受邀者不能确认域是否存在；
- 匿名用户不能读取；
- 公开静态站点属于未来独立导出能力；
- 底层不存在 `public_build` 特殊密码协议。

## 7. 内容与文件策略（v0.2 当前冻结基线）

### 7.1 核心字节模型

- 同步核心把受支持的普通文件视为不透明字节流；
- 加密、清单、存储和快照恢复不依赖 Markdown 或代码语义；
- 产品层使用版本化允许列表决定哪些文件可以进入正式快照；
- 扩展允许列表不应要求修改底层加密对象格式；
- 发现未支持的普通文件时必须报告 `UnsupportedFilesFound` 并阻止快照正式完成，不能静默遗漏；
- P0 默认拒绝 Symlink、Junction 和其他重解析点：不跟随、不上传、不恢复，并给出明确错误；
- 不允许任何扫描或恢复路径逃出指定 Vault 根目录。

### 7.2 P0 默认允许列表

P0 至少同步并保留以下文件的原始字节和 Vault 相对路径：

- `.md`；
- `.canvas`；
- `.pdf`；
- `.png`、`.jpg`、`.jpeg`、`.gif`、`.webp`；
- `.c`、`.h`、`.cpp`、`.hpp`、`.py`。

“主流语言文件”不是可执行的范围定义。其他代码扩展名必须通过版本化内容策略逐项加入，不能依靠模糊分类自动扩大正式支持范围。

### 7.3 P1 展示和协调语义

- `.canvas` 在 P1 中按整文件同步、版本化和冲突处理，不做节点级语义合并；
- 图片和 PDF 在发生并发修改时按整文件协调；
- Markdown 和后续明确支持的文本代码文件可以在 P1-alpha 评估确定性文本三方协调，但不属于当前 P0；
- 系统保证用户能看到所有 Markdown 文字、打开已同步附件，并保持原始路径；
- 渲染差异和第三方插件渲染问题交给 Obsidian；
- P0/P1 默认不处理 `.obsidian`、社区插件、主题和设备专属配置；
- P1 暂不承诺音频、视频和任意大型二进制类型；
- 不允许同步操作写出 Vault 根目录。

## 8. 域激活硬门槛（已冻结）

任何域在首次上传前必须完成恢复材料设置，不存在七天宽限或降级试用。

```text
LocalPrepared
    ↓
RecoverySetupPending
    ↓ 完成恢复材料保存和持有性验证
PossessionVerified
    ↓ 原子激活
Active
```

在 `Active` 之前：

- 服务端不得接收 Vault 正文、附件、路径或文件名；
- 不允许绑定第二台设备；
- 不允许邀请团队成员；
- 不能仅通过勾选“我已保存”完成验证；
- 用户可以继续使用 Obsidian 在本地编辑原 Vault。

恢复凭证必须由密码学安全随机数生成器产生。安全定义按随机熵和密钥角色描述，不能只写“16 位”；具体编码和密码协议待技术设计冻结。

P0 使用同一组状态名实现本地激活门槛，但其中 `Active` 只表示“允许创建 P0 加密快照”，不表示已经具备生产服务器、真实多设备同步或生产安全资格。P0 的持有性验证必须重新读取保存在 Vault 外的恢复文件；仅依赖勾选框、内存中尚未清除的密钥或源进程状态均不合格。

## 9. 初始来源与设备绑定（已冻结）

### 9.1 首次创建个人域

- 已使用一年的电脑 Vault 无条件成为初始 Source of Truth；
- 手机端无论为空或含默认文件，都只能作为接收方；
- 手机已有文件不得反向污染初始电脑 Vault；
- 手机非空目录需要隔离、换空目录或明确处理；
- 初次全量接收完成以后，各设备成为普通对等同步端。

### 9.2 设备身份

- 同一域在不同设备共享 `domain_id` 和域历史；
- 每台设备拥有独立 `device_id`、设备密钥和同步状态；
- 设备私钥不离开设备；
- 吊销一台持有当前解密能力的设备需要建立新的全域加密代际。

### 9.3 绑定流程

推荐交互：

```text
新设备发起请求
    ↓
可信设备显示动态验证码或短认证串
    ↓
新设备输入并完成双向握手
    ↓
初次只接收
    ↓
验证完成后 Active
```

团队域规则：

- 成员首次加入的第一台设备必须由域主批准；
- 成员第二台及后续设备由该成员自己的现有可信设备批准；
- 域主不介入普通成员的后续设备管理；
- 没有可信设备时，必须进入明确的恢复流程。

## 10. 角色与权限（已冻结）

### 10.1 角色

- **域主**：所有权、恢复根、最终成员治理和高风险清除；
- **管理员**：内容审核、正式发布、普通成员紧急隔离等受限治理能力；
- **贡献成员**：读取当前 Vault，制作和提交候选修改；
- **阅览成员**：读取当前 Vault 和加入后的同步，不提交候选修改。

### 10.2 核心权限矩阵

| 能力 | 域主 | 管理员 | 贡献成员 | 阅览成员 |
|---|---:|---:|---:|---:|
| 读取当前完整 Vault | 是 | 是 | 是 | 是 |
| 读取加入后的历史 | 是 | 是 | 是 | 是 |
| 提交候选修改 | 是 | 是 | 是 | 否 |
| 批准他人候选 | 是 | 是 | 否 | 否 |
| 普通批准自己的候选 | 否 | 否 | 否 | 否 |
| 创建正式命名发布 | 是 | 是 | 否 | 否 |
| 邀请成员第一台设备 | 是 | 否 | 否 | 否 |
| 隔离普通成员 | 是 | 是 | 否 | 否 |
| 隔离管理员 | 是 | 否 | 否 | 否 |
| 永久移除成员 | 是 | 否 | 否 | 否 |
| 解除隔离并重新准入 | 是 | 否 | 否 | 否 |
| 转让所有权 | 是 | 否 | 否 | 否 |
| 撤销发布保留锚点 | 是 | 否 | 否 | 否 |
| 跨发布内容清除 | 是 | 否 | 否 | 否 |

### 10.3 阅览成员的诚实边界

- 阅览成员持有域内容解密能力；
- “只读”只约束其向团队权威状态提交修改，不能阻止复制和本地编辑；
- 邀请时必须提示其会取得当前完整内容的永久本地副本；
- 阅览成员被隔离、移除或退出时，同样触发全域加密代际切换。

## 11. 加入、退出和密钥代际（已冻结）

### 11.1 新成员加入

- 加入授权只能由域主可信设备签名；
- 授权绑定账号、域、角色、具体新设备公钥、有效期和随机数；
- 域主或管理员可信设备可以执行已经由域主签署的密钥交付；
- 管理员不能自行产生准入授权；
- 服务器只能转发签名授权和加密密钥包；
- 普通网页登录不是可信设备，除非完成正式设备注册并持有本地私钥。

新成员获得：

- 加入正式生效时不可变域状态的完整当前快照；
- 加入以后产生的可访问历史。

新成员默认不获得：

- 加入前已经失效的文档修订；
- 已删除文件；
- 旧附件；
- 私有草稿和未发布候选。

加入边界由不可变 `Domain State` 决定，不由人类可读发布版本号决定。

### 11.2 成员退出和隔离

退出或隔离必须原子完成：

1. 吊销目标成员在当前域中的全部设备；
2. 撤销其尚未批准的候选修改；
3. 切换整个域的共享加密代际；
4. 向所有剩余活跃设备封装新密钥包；
5. 阻止目标成员读取未来域状态；
6. 写入签名审计。

旧代际停止用于新状态，但合法成员设备仍可保留旧代际以读取其有权访问的历史。系统不能让退出成员忘记已下载内容，也不尝试远程擦除其 Vault。

### 11.3 管理员安全隔离

- 管理员只能安全隔离普通成员；
- 管理员不能隔离域主或其他管理员；
- 安全隔离立即生效，不等待 AI；
- 只有域主能够永久移除或解除隔离；
- 解除隔离是重新准入，不是恢复旧凭证；
- 域主解除时必须填写解除原因；
- 隔离原因与解除原因作为成对、不可修改的加密审计展示。

## 12. 恢复模型（已冻结）

### 12.1 域主恢复

- 个人域和团队域的域主使用高熵离线恢复材料；
- 账号密码绝不能单独恢复域；
- 解密完全在新设备本地发生；
- 域主恢复当前快照和仍在保留策略内的完整域历史；
- 不恢复从未上传的成员本地草稿或已经密码学清除的内容；
- 成功恢复前必须生成、保存并验证新的恢复密钥；
- 恢复、旧设备吊销、全域密钥换代和恢复密钥换代原子完成；
- 旧恢复材料可能仍能解开其过去对应的旧副本，但不能取得轮换后的未来秘密。

### 12.2 普通成员救援

普通成员丢失全部可信设备时：

- 先登录自己的账号；
- 新设备本地产生设备公私钥；
- 域主针对具体域、账号、请求和设备公钥签署恢复授权；
- 域主通过独立渠道提供 8 位短时一次性救援码；
- 8 位码只用于身份确认，不参与任何域密钥派生；
- 救援码短时有效、严格限速、单次使用；
- 成功后吊销该成员在当前域的全部旧设备并进行全域换代；
- 新设备只获得恢复时的当前快照和未来历史，不补发恢复前的失效历史；
- UI 必须说明这是“恢复当前工作能力”，不是“恢复全部历史”。

如果仍有一台旧可信设备，则属于正常设备绑定，新设备可以继承该成员原有历史访问范围，不走域主救援码流程。

### 12.3 所有权转让

- 所有权转让是历史保管权转移，不只是修改 `owner_id`；
- 新域主会获得域保留策略内的完整正式历史，包括其加入以前的内容；
- 新域主必须在可信设备上生成并验证新的离线恢复材料；
- 转让、全域换代、治理权撤销和恢复根换代原子完成；
- 失败时原域主继续拥有所有权，不能出现双域主或无域主；
- 旧域主不能取得转让后的未来秘密，但无法被迫忘记过去已经获得的内容。

### 12.4 P0 快照恢复的术语边界

P0 的“快照恢复”是验证本地加密闭环的工程术语：新进程仅凭 Vault 外恢复文件和不可信 ObjectStore 中的密文，将一个不可变快照恢复到新建空目录。

- P0 快照恢复不等于本节 12.1 的正式域主恢复；
- P0 只有单用户、单快照，不涉及旧设备吊销、成员权限或全域换代；
- 恢复目标必须是新建空目录，源 Vault 始终只读；
- 恢复成功必须由独立验证器逐文件核对相对路径和字节；
- 正式域主恢复、设备吊销与全域换代仍属于 P1-alpha 以后。

## 13. 本地同步与冲突模型（已冻结）

### 13.1 四个逻辑层

- **Base**：本地 Working 所基于的最后确认团队状态；
- **Working**：用户磁盘上真实存在、可继续编辑的文件；
- **Incoming**：从服务器取得、尚未污染 Working 的新状态；
- **Reconciliation Preview**：三方比较与可视化确认结果。

存在本地草稿时，Incoming 进入隔离缓存或暂存区，不能直接覆盖物理文件。

### 13.2 典型冲突 UI

冲突提示至少包含：

- 文档位置；
- 被修改位置和行号；
- 自动兼容的部分；
- 需要人工选择的元数据或结构变化。

用户级选择包括：

- **升级我的离线改动，适配新版本**：把本地意图重放到新结构；
- **保留本机旧结构**：用本机整篇文档覆盖该篇当前版本，并明确警告会放弃另一端对该篇的全部修改；
- **分开处理，我仔细看每一项**：逐项协调。

不变式：

- 选择只作用于当前发生冲突的文档；
- 绝不波及同一次同步中的其他文件；
- 不向用户显示 `<<<<<<<` 等 Git 冲突符号；
- 覆盖前保留可回滚历史，并标记内容来源偏离；
- 如果当前存在未提交编辑，阻止会覆盖它的历史恢复。

## 14. 版本模型（已冻结）

系统区分：

1. **Candidate Revision**：Proposal 中尚未进入团队状态的不可变候选版本；
2. **Document Revision**：已经进入正式域历史的单篇文档修订；
3. **Domain State**：服务端串行确认的不可变完整域状态；
4. **Named Release**：域主或管理员基于某个既有 Domain State 创建的命名快照和保留锚点。

### 14.1 恢复规则

- 恢复永远产生新的 Document Revision 和 Domain State，不倒退版本号；
- no-op 恢复不增加文档修订或域状态，只记录操作日志；
- 恢复已删除文档会产生新修订和新域状态；
- 恢复和普通编辑使用同一条服务端串行化通道；
- 单篇恢复只影响当前文档；
- 单篇恢复不出现在正式发布时间线上；
- 文档历史显示恢复前后差异；
- 最新发布详情可以显示发布后发生的单篇恢复或点修改；
- 任意整库时间点恢复不属于当前 P1 已冻结范围。

## 15. Proposal 与审核（已冻结）

### 15.1 基本语义

- 本地修改在提交前只对作者可见；
- Proposal 是稳定的审核线程；
- 一个 Proposal 可以包含多个不可变 Candidate Revision；
- 作者更新候选时创建新 Candidate Revision，不能覆盖审核者已查看的内容；
- 批准签名绑定具体 Proposal、Candidate Revision、Base Domain State 和内容清单承诺；
- 只有最终合并候选进入 Document Revision 与 Domain State；
- 中间候选不会永久污染正式知识历史。

### 15.2 状态

```text
DraftLocal
    ↓
UploadedPendingReview
    ├─ ChangesRequested
    ├─ ApprovedPendingCapacity
    ├─ Merged
    ├─ RejectedRetained
    ├─ WithdrawnPendingPurge
    └─ ExpiredPendingPurge
```

### 15.3 生命周期

- 作者在正式批准或拒绝前有无理由撤回权；
- 撤回只终止服务器后续交付，不能让已解密审核者遗忘内容；
- 撤回内容立即移出活跃索引，无其他引用的密文最迟 7 天从主存储清除；
- 被拒绝候选内容保留 30 天；
- 长期待审 Proposal 从首次提交起最长保留 90 天；
- 新 Candidate Revision 不重置 90 天期限；
- 到期后清除正文、附件和 Diff，只保留不含内容的最小审计；
- 作者本地 Working 在撤回、拒绝和过期后仍保持原样。

### 15.4 请求修改

- 审核者可以请求修改而不直接拒绝；
- 请求修改必须包含具体理由；
- 作者在同一 Proposal 中提交新的不可变 Candidate Revision；
- 作者更新与审核者批准并发时，以服务端串行顺序决定结果；
- 审核者只批准当前精确候选版本。

### 15.5 多文件原子合并

- 一个 Proposal 可以包含新增、修改、删除、移动、重命名、附件和 Canvas；
- P1 不支持部分批准；
- 审核者可以逐篇检查和评论，但最终整体原子合并；
- 任一冲突、配额不足或完整性失败都会阻止整个合并；
- 作者可以显式拆分成新的 Proposal，服务器不自动切割依赖。

### 15.6 审核人数和风险

- 普通 Proposal 只需要一名非作者域主或管理员批准；
- 作者不能普通批准自己；
- 风险不增加第二名审核者，而是采用确定性分级；
- `Standard`：普通完整预览；
- `WideImpact`：强化影响预览、强制理由、签名确认和域主通知；
- `BlockedByInvariant`：任何人都不能通过风险勾选绕过；
- AI 可以本地辅助提示，不能改变确定性权限和协议不变式；
- 影响阈值的具体数字待真实 Vault 试用后冻结。

## 16. 紧急能力（已冻结与待细化）

### 16.1 域主和管理员紧急自我合并（已冻结）

域主和经域主预授权的管理员可以在极窄范围内使用紧急自我合并，但适用相同限制：

- 只允许无冲突、`Standard` 风险、低规模修改；
- 仅允许受限 Markdown 内容和少量内部链接；
- 不允许删除、移动、重命名、附件、PDF、图片和 Canvas；
- 必须有完整 Proposal 和 Candidate Revision；
- 必须填写理由；
- 必须通过确定性检查和本地 AI 风险筛查；
- AI 不可用、失败、输出无效或要求升级时必须失败关闭；
- 每人滚动 24 小时最多 3 次；
- 成功后立即通知并写入不可篡改审计；
- 不自动创建 Named Release；
- 本地 AI 组件未达到验收标准前，该入口不得上线。

### 16.2 紧急治理恢复（高层方向已接受，P1 精确范围待裁决）

已接受的高层方向：

- 域主拥有管理员没有的紧急治理恢复通道；
- 只用于撤销或回滚已经进入域状态的错误变化；
- 不用于主动推送新内容；
- 可以涉及 P1 支持的任意文件类型；
- 不能改写原历史。

当前建议但尚未最终冻结的 P1 精确范围：

- 只允许反向一项已经正式合并的 Proposal；
- 输出必须可确定性证明来自仍被保留的既有正式历史；
- 不依赖 AI，不受 3 次/24 小时限制；
- 不允许部分成功；
- 产生新的反向 Domain State；
- 不自动修改旧 Named Release；
- 不支持任意整域时间点恢复；
- 管理员是否可以向域主提交签名恢复建议仍待裁决。

## 17. 正式发布（已冻结）

### 17.1 创建权限和语义

- 域主和管理员可以创建 Named Release；
- 不需要第二人复核；
- 只能引用已经成为团队事实的不可变 Domain State；
- 不能直接发布本地 Working 或未批准候选；
- 创建发布不会改变当前文档内容；
- 发布记录、保留引用和配额预留原子提交。

### 17.2 保留锚点

正式发布是长期精确重建锚点：

- 被仍有效发布引用的文档修订和附件不受普通过期策略影响；
- 多个发布引用同一密文对象时，实际存储只计一次；
- 撤销一个发布锚点不能删除仍被其他发布或当前状态引用的对象；
- 域主可以撤销发布保留锚点，但发布曾经存在的记录不能被抹去；
- 撤销锚点与跨发布敏感内容清除是不同操作。

### 17.3 管理员发布的资源约束

- 发布前展示完整快照规模和本次新增唯一保留成本；
- 超过域主软阈值时不要求第二人批准，但必须强化确认、填写说明并通知域主；
- 任何发布不得突破域硬存储配额；
- 只有域主可以增加额度或撤销旧发布保留锚点；
- 预览绑定具体 Domain State，不能用旧预览确认变化后的状态。

## 18. 历史保留策略（当前冻结基线）

| 数据类别 | P1 基线 | 到期语义 |
|---|---:|---|
| 活跃 `.md` 历史 | 域生命周期内保留 | 域主清除或域删除时进入清除流程 |
| 活跃 `.canvas` 历史 | 域生命周期内保留 | 按整文件历史处理 |
| 已删除 `.md` / `.canvas` 及其全部内容历史 | 90 天 | 到期后正文和修订失去域内恢复能力，只留最小墓碑与审计 |
| 被覆盖但仍活跃的旧图片 / PDF | 30 天 | 无发布锚点时到期清除 |
| 被整体删除的图片 / PDF | 90 天 | 当前和仍保留的旧版本共同进入清除窗口 |
| 当前活跃图片 / PDF | 活跃期间 | 删除后进入 90 天窗口 |
| 域内治理审计 | 域生命周期内 | 整域删除后按域删除策略处理 |
| 服务运营日志 | 待部署与法务边界确定 | 与 E2EE 治理审计分离 |

补充：

- 一旦整篇 Markdown 或 Canvas 被删除，其所有内容修订共同进入 90 天窗口，不能利用“活跃文档历史长期保留”绕过删除；
- “永久”表示域生命周期内，不表示用户删除域后运营方仍永久持有；
- 存储优化可以使用内容寻址、分块去重、检查点和增量编码，但不能牺牲独立恢复任一合法修订的能力；
- 不承诺所有历史只存 Diff；
- 保留倒计时以服务端串行确认时间为准，不使用可修改的客户端文件时间。

## 19. 跨发布内容清除（已冻结）

域主可以针对误发布的敏感修订或附件执行跨发布内容清除：

- 操作只针对明确对象；
- 产生新的不可变清除事件，不修改原发布记录；
- 目标从当前恢复包和所有发布恢复路径移除；
- 受影响发布永久标记为不完整；
- 所有当前和未来成员能够看到发布不完整提示；
- 详细原因、对象标识和带密钥内容承诺只进入加密治理审计；
- 不向服务器或无权成员公开裸明文哈希；
- 被清除旧修订不能重新挂回原发布；
- 未来同名同内容文件可以作为新修订进入新状态或新发布；
- 管理员不能执行；
- 已下载到成员设备的副本无法远程收回。

跨发布清除是支持适用数据删除请求的技术基础之一，但不单独构成 GDPR 或其他法域的完整合规声明。

## 20. 配额与内容只读保险丝（已冻结）

### 20.1 三类资源边界

- 正式域内容额度；
- 候选修改暂存额度；
- 独立的安全控制面资源。

配额按实际唯一密文字节计算，不进行泄露明文相等关系的跨域去重。

### 20.2 配额耗尽

正式内容空间耗尽时，域进入 `QuotaExceededReadOnly`：

- 本地编辑继续；
- 新内容不上传；
- 个人域修改显示 `LocalOnlyPendingCapacity`；
- 团队候选可能上传到独立暂存额度，但暂存额度也有上限；
- 已批准但容量不足的候选进入 `ApprovedPendingCapacity`；
- 不自动删除历史；
- 不自动缩短保留期；
- 不破坏正式发布。

始终允许：

- 下载和恢复已有数据；
- 设备吊销；
- 成员隔离与移除；
- 密钥换代；
- 所有权转让；
- 导出；
- 删除和清理；
- 整域删除；
- 必要安全审计。

内容配额绝不能阻止安全控制面。

## 21. 域删除（已冻结）

### 21.1 30 天封存后悔期

```text
Active
    ↓ 域主请求删除
DeletionPending（固定 30 天）
    ├─ 使用账号认证 + 离线恢复材料撤销
    │      ↓
    │  RecoveryRekeyPending
    │      ↓ 新恢复密钥 + 全域换代
    │  Active
    └─ 到期
           ↓
       Destroying
           ↓
        Deleted
```

进入 `DeletionPending` 后：

- 云端域立即封存；
- 停止上传、下载、邀请、审核、发布和治理写入；
- 本地 Vault 保持可读可写；
- 本地新修改只作为本地 Working；
- 服务器保持删除请求时的精确密文状态；
- 通知所有当前成员。

### 21.2 撤销删除

- 只有域主可以撤销；
- 必须同时具备账号认证、离线恢复材料和新设备密钥；
- 恢复材料不上传服务器；
- 撤销后必须生成并验证新的恢复密钥；
- 执行全域密钥代际切换；
- 封存期间本地修改重新走普通三方协调和团队审核。

### 21.3 最终销毁

30 天到期并由服务端串行确认后：

- 原域不可恢复；
- 账号、恢复密钥、管理员和客服都不能重新激活；
- 原 `domain_id` 永久终结；
- 服务端对象进入明确的主存储与备份清除流程；
- 本地成员副本不受影响；
- 原本地 Vault 可以创建一个全新域，但不能冒充旧域复活。

主存储和备份的具体物理删除 SLA 待部署方案确定。

## 22. 域删除时的本地保全（已冻结）

系统必须提供：

- 本地副本完整性报告；
- 最后确认 Domain State 和同步时间；
- 本地修改、缺失附件和不支持文件提示；
- “基于当前设备的本地文件创建个人域”入口。

创建新个人域时：

- 必须复制到新的 Vault 文件夹；
- 原团队 Vault 不修改、不删除、不原地转换；
- 新域使用新的 `domain_id`、密钥、恢复包和历史；
- 新域只包含当前磁盘实际存在的文件；
- 相对路径和文件字节保持不变；
- `.obsidian` 默认排除；
- 不继承原团队历史、发布、成员、审计或权限；
- 如果原团队域后来恢复，两个域继续独立，不自动合并。

## 23. AI 边界（已冻结）

- AI 默认在本地可信设备运行；
- 云端 AI 只能在用户针对具体域、具体对象、具体修订和具体任务进行单次显式授权后接收临时明文；
- 明文出域必须记录；
- AI 不能替代确定性权限、配额、路径和完整性验证；
- AI 不能声称“确保安全”；
- AI 不可用时，依赖 AI 的紧急功能必须失败关闭；
- AI 生成的发布说明、风险提示和建议默认不自动执行。

P0 运行时不得包含 AI 组件。AI 可以用于开发辅助、测试数据生成或离线分析报告，但不能参与密钥生成、权限判断、路径验证、完整性判断、域激活或快照恢复。

## 24. 未来公开发布（P3，方向已冻结）

匿名公开内容不属于 P1 团队域访问模式。未来流程应是：

```text
E2EE 团队域中的正式发布
    ↓ 域主在可信设备显式选择
本地解密、渲染和导出
    ↓
独立静态只读副本
    ↓
独立公开 URL / CDN
```

- 静态托管不拥有团队域根密钥；
- 只导出被明确选择的 Named Release；
- 不导出当前 Working、候选修改和治理审计；
- 公开副本与团队域的删除、撤回和缓存处理是不同操作；
- 公开内容一旦被第三方复制，无法通过 E2EE 域远程收回。

## 25. 核心验收场景

P0 的先行验收场景是“本地加密快照与新进程恢复”：在 Windows 上选择只读测试 Vault，生成并重新读取 Vault 外恢复文件，将密文写入本地不可信 ObjectStore，结束源进程和本地工作状态后，在新建空目录恢复，并由独立验证器证明受支持文件的相对路径与字节完全一致。模拟服务器不得出现原始正文、文件名、扩展名、相对路径或裸内容哈希。详细门槛见 [`docs/product/P0_EXECUTION_PLAN.md`](docs/product/P0_EXECUTION_PLAN.md)。

### 25.1 个人多设备同步

1. 用户以已经使用一年的电脑 Vault 创建个人域；
2. 完成恢复密钥保存验证后首次上传；
3. 手机作为接收方绑定；
4. 电脑修改一篇文章；
5. 手机联网并打开 Obsidian 后出现更新；
6. 原始 Markdown、附件和相对路径不变。

### 25.2 个人离线冲突

1. 手机离线修改旧版本；
2. 电脑推进新版本并改变元数据结构；
3. 手机上线后无冲突段落自动协调；
4. 跨版本元数据变化进入卡片式选择；
5. 用户不处理 Git 冲突符号；
6. 选择只影响当前文档。

### 25.3 团队审核

1. 域主创建团队域；
2. 邀请贡献成员和阅览成员；
3. 成员第一台设备由域主批准；
4. 贡献成员本地修改并提交 Proposal；
5. 非作者域主或管理员审核；
6. 请求修改时作者提交新的 Candidate Revision；
7. 最终候选原子合并为新 Domain State；
8. 所有活跃成员收到新的当前快照。

### 25.4 成员隔离

1. 管理员隔离普通成员；
2. 目标成员全部域设备立即失效；
3. 全域共享加密代际切换；
4. 所有剩余成员取得新密钥包；
5. 目标成员保留本地旧内容，但不能获得未来状态；
6. 域主解除时填写与隔离原因配对的理由并重新准入。

### 25.5 恢复

- 域主恢复能够在本地解开当前状态和仍被保留的完整历史；
- 恢复成功前必须保存并验证新的恢复密钥；
- 普通成员 8 位救援码不能离线解密任何内容；
- 普通成员全设备丢失恢复只取得当前快照和未来历史。

### 25.6 发布与保留

- Named Release 能精确重建其引用状态；
- 被发布引用的旧附件不因普通 30 天期限过期；
- 管理员发布不能突破硬配额；
- 跨发布清除后，原发布仍存在但永久标记为不完整。

### 25.7 配额

- 正式内容配额耗尽时，本地编辑不丢失；
- 云端新增停止；
- 下载、恢复、隔离、吊销和换代仍然可用；
- 系统不会自动牺牲历史换取空间。

## 26. 建议的阶段切分（尚未冻结为排期）

### P0：协议与本地引擎原型

- 冻结 P0 子集、威胁模型、安全不变式和密钥生命周期；
- TypeScript 共享核心、CLI、Python 独立验证器和极薄 Windows Obsidian 插件；
- Android Obsidian 只做共享核心与候选密码实现的兼容性 smoke test；
- 只读 Vault 扫描、版本化内容策略和加密 Manifest；
- 单个 Vault 外高熵恢复文件及持有性验证；
- 本地认证加密、密文对象格式和不透明对象标识；
- Directory ObjectStore 中的不可变快照；
- 新进程向新建空目录执行 P0 快照恢复；
- 10,000 文件、约 1 GiB 代表性 Vault 的完整往返和有界内存测试；
- 服务器可见性、篡改、缺失对象、路径逃逸、崩溃和非空目标测试；
- 本地目录闭环通过后，再实现 localhost HTTP ObjectStore 适配器；
- 不涉及真实账号、真实团队、生产服务器、自动监听、增量同步或冲突协调。

### P1-alpha：个人多设备同步

- 桌面端与一个移动平台；
- 域激活硬门槛；
- 现有电脑 Vault 作为 Source of Truth；
- 设备绑定；
- 当前快照和历史；
- 文件监听和增量同步；
- Base / Working / Incoming；
- 确定性三方协调实验和端侧冲突 UI；
- 域主离线恢复；
- 配额保险丝。

### P1-beta：邀请制团队协作

- 账号与成员准入；
- 域主、管理员、贡献成员、阅览成员；
- 群组密钥代际；
- Proposal、Candidate Revision、请求修改和原子合并；
- 成员隔离、退出和恢复；
- 团队试用与风险阈值校准。

### P1-release：治理与长期历史

- Named Release 与保留锚点；
- 分层保留；
- 跨发布清除；
- 域删除后悔期；
- 所有权转让；
- 正式恢复和审计验收。

### P2

- 达到验收标准的本地 AI 风险组件；
- 管理员和域主紧急自我合并；
- 更丰富的审核分配和治理恢复；
- 高级历史授权；
- 更完善的存储优化和迁移。

### P3

- 从 Named Release 显式导出的公开静态站点；
- 独立托管、缓存、撤回和公开内容治理。

## 27. 阶段化裁决清单

### 27.1 已形成且当前仍有效的 P0 决策

1. 当前 P0 是本 README 原 P0 设想的严格子集，以本地加密快照和新进程恢复为第一个可验证闭环；
2. 开发者为一人，平均每天约一小时，无硬截止日期；
3. 首批平台顺序为 Windows 主开发、Android 兼容性验证和后续 P1-alpha 支持，iOS 后置；
4. 移动端只承诺打开 Obsidian 后运行，不承诺 Obsidian 关闭后的后台同步；
5. TypeScript 是共享核心和插件主语言，Python 只作为独立验证和测试辅助；
6. P0 使用单个 Vault 外高熵恢复文件；
7. ObjectStore 先实现本地目录适配器，通过本地闭环后再实现 localhost HTTP 适配器；
8. P0 只接受当前格式产生的不透明域/object ID、对象数量、密文大小、访问时间、Object/协议/suite 版本和 nonce/ciphertext/tag 长度；P0 不引入 mutable `head`，状态序号和加密代际留待后续状态协议定义，不做大小或流量填充；
9. P0 运行时零 AI；
10. P0 的代表性规模为 10,000 文件、1 GiB ±5%；当前 peak RSS 上限为 512 MiB，只能按 DP-011 调整一次；
11. Recovery File v1 是含 32 字节 recovery root 的 167 字节 bearer file；object ID 固定 16 原始字节/22 字符 base64url store key；Manifest AAD 所需 snapshot ID 先由恢复文件提供；
12. 37 ACC / 16 INV / 5 THR 和 26 个延期项以 `docs/contracts/` 的机器 registry 为准。

### 27.2 历史：审查基线 b8f15fc 仍需关闭的门槛（已被当前合同取代）

以下 10 条只描述 `b8f15fca1d7a1bb31bb6b2693103da73c85588fe` 时的历史缺口，不是当前状态。其旧结论不得单独引用；当前裁决见 §27.3 和 consistency 文件。

1. 威胁模型、安全不变式与验收项之间还缺少稳定的 Threat ID、完整映射和可执行 oracle；
2. 候选密钥图已经形成，但 KDF 参数、独立对象密钥包装密钥、nonce 策略和用途隔离编码仍待 smoke test 后通过 ADR 冻结；
3. P0 不引入设备签名和 mutable `head` 的方向已经接受，但完整旧快照替换/回滚目前没有外部新鲜度锚点，必须明确记录为 P0 不提供的保证，不能写成风险不存在；
4. 恢复文件已增加 Manifest 定位符，但恢复材料究竟冻结为 bearer secret 还是引入会改变 INV-11 的外部解锁密钥、恢复文件完整性覆盖/密钥来源以及整体替换安全声明仍待补充 ADR 裁决；
5. crypto smoke 的 `candidate × algorithm suite × environment` 矩阵、环境/报告 schema、算法级 KAT 和错误 oracle 尚未冻结；具体依赖版本、lockfile、bundle hash 与 Android 真机报告是后续获授权执行 Phase 1 时的产物，它们阻止候选库选型，但其尚不存在本身不与“Phase 1 尚未开始”矛盾；
6. Manifest、恢复文件和密文对象只有逻辑格式要求，具体字节布局、AAD、版本、对象 ID 位数/编码和碰撞策略尚未冻结；
7. Windows NTFS 路径规则仍需补齐 canonicalization、Unicode、保留设备名、ADS 和校验后重解析点替换等边界；
8. 10,000 文件、约 1 GiB fixture 的精确分布、生成器、性能采集方法和第一份基线尚不存在；
9. 37 条验收项当前全部是 `untested`，仓库中没有对应实现、脚本或证据；所有 required/in-scope 项通过前不得关闭 P0-R1；

## 28. 工程原则

- 不自行发明底层密码算法；优先使用成熟、经过审查的密码库和标准结构；
- 在选定协议前先写威胁模型和密钥生命周期；
- 所有权限决策绑定不可变状态、具体设备和签名；
- 服务端串行化不等于服务端可以伪造内容；
- 所有不可逆操作先明确目标、影响和恢复边界；
- 所有合并、恢复、发布、配额和密钥换代必须可进行原子性测试；
- 日志不得记录明文正文、路径、密钥或裸内容哈希；
- 客户端异常、断网和磁盘空间不足不得损坏原 Vault；
- 所有“安全”“合规”“无法解密”声明必须由实现、测试和审计证据支持；
- 负面结果和被排除的能力应当明确记录，不用宣传语言掩盖。

## 29. 当前结论

这个设想已经足以构成一个值得投入和写入简历的项目，但前提是严格分阶段。

真正有价值的部分不是“又写了一个 Obsidian 同步插件”，而是：

- 用清晰域模型连接本地文件、设备、成员、版本和恢复；
- 在 E2EE 条件下处理团队密钥演进；
- 用三方协调和可视化选择保护离线草稿；
- 把候选审核、正式历史、发布保留和删除语义分开；
- 对配额、恢复、退出和误操作给出可验证的不变式。

当前 P0 的设计合同已经完成静态修复：恢复链不再循环依赖，canonical wire bytes 和 schema 有机器权威，37/16/5 追踪可运行检查，延期项有硬门禁，schema 强制路径由 `--validate-samples` 用正/负样本反身校验。Phase 1 正式矩阵、Phase 2 Tiny fixture/scanner/Manifest、Phase 3 Recovery/Object crypto/Directory ObjectStore，以及 Phase 4-A snapshot 编排均已按各自授权完成；Phase 4-B 恢复实现正在处理第一轮独立复审 finding，仍未提交。P0-R1 正式 evidence 与任何 passed ACC 仍不存在；这些实现和 dirty-source 测试不等于生产安全或 P0-R1 关闭。
