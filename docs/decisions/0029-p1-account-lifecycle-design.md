## 1. 背景与边界

ADR-0028 裁决并行模式：设备本地为默认（无账号），中心托管推迟到 P1-release 且以本设计（DP-017）为前置。本 ADR 冻结账号体系的**模型方向与硬边界**——它约束未来实现合同的形状，但不是实现授权；真实账号实现（含服务端）需在 P1-release 前另立合同。

## 2. 设计冻结（方向与边界）

1. **账号 = 托管层身份，不参与端到端信任**：账号存在仅为中心托管模式的服务编排（对象存储配额、head 指针托管、设备注册代理）；E2EE 信任根仍是设备密钥与 head 链签名（ADR-0026），账号凭据泄露**不等于**域密钥泄露。
2. **认证方向（待确认点 1）**：Passkey 优先（WebAuthn，无密码库、防钓鱼、天然双因子：绑定设备 + 生物/PIN）；恢复码兜底（账号丢失主力 Passkey 后经一次性恢复码重注册登录）；密码+TOTP 作为备选方向。
3. **恢复硬边界（冻结为不变式候选 INV-19）**：**账号恢复 ≠ 域密钥恢复**。托管方在任何情况下都无法恢复端到端域密钥；"恢复"仅指：经既有已授权设备批准，或经恢复码，把**新设备**注册进 devices 体系。任何"服务器恢复域"的宣称都被本设计禁止。
4. **删除语义（与 DP-021 联动）**：账号删除 = 托管层删除（账号元数据 + 托管密文对象按 DP-021 SLA 清除）；客户端本地副本与用户自持密钥不在服务器能力范围内——删除声明必须限定为"托管层删除"。设备在删除前导出 head 链与恢复材料后可离线继续。
5. **滥用/恢复威胁 delta（DP-017 close_artifact 的具体化，registry 翻转随 P1-release 实现合同）**：新增威胁候选——THR-06（恶意批量注册与资源滥用：缓解方向 = 创建质询/限流）、THR-07（恢复流程钓鱼：缓解方向 = 恢复仅经既有设备端内确认，服务器永不发起"点此恢复"凭据收集）。该 delta 文本随实现合同入册。
6. **与状态协议的衔接**：devices.json 的远期演进 = 托管设备注册表的服务端镜像（账号绑定设备列表）；本设计不改变 ADR-0026 的本地 devices.json 语义。

## 3. 待开发者确认的三个确认点

> 设计尚未裁决（2026-09-05 本轮仅交付设计材料）。三条确认点均推荐按"推荐"选项接受：Passkey 优先 / 冻结 INV-19 / 设计完成即关闭 DP-017。

1. **认证方向**：Passkey 优先 + 恢复码兜底（推荐）；或密码 + TOTP。
2. **恢复边界**：冻结"账号恢复 ≠ 域密钥恢复"为不变式候选 INV-19，恢复仅指设备重注册（推荐）；或引入托管方协助的密钥恢复（改变 INV-11/信任根，不推荐）。
3. **DP-017 关闭时点**：本设计 ADR 接受即关闭 DP-017（设计完成；实现合同属 P1-release 前置，另立）（推荐）；或保持 deferred 至实现临近。

## 4. 后果

- 接受后新增 wire token `P1_ACCOUNT_LIFECYCLE_DESIGN_ACCEPTED`；DP-017 按确认点 3 裁决；DP-021（删除 SLA）保持 deferred 并新增"托管层删除"联动注记。
- 本 ADR 不授权任何实现；中心托管的服务端实现合同在 P1-release 前起草，届时必须落实 §2.5 的 THR-06/07 registry 翻转。
- 设备本地默认形态（ADR-0028）不受影响：无账号路径继续零依赖可用。
