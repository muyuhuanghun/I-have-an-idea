# ADR-0032：P1-beta Proposal key 的审核者分发与撤销设计（DP-018）

- 状态：**已接受（2026-09-12）——开发者委托裁决（"开工 DP-018，完成后自行从管理者、用户、部署等方面检查"），本 ADR 采纳推荐选项并经四视角两轮自检；任何裁决可被开发者事后否决，否决即回滚关闭状态**
- 日期：2026-09-12
- 决策者：开发者（OWNER-SECURITY 归属；本轮由开发者委托按推荐路径裁决）
- 阶段：P1-beta team proposal design（DP-018 关闭切片，纯设计，不含实现）
- 相关文档：DP-018（registry）、ADR-0026/0027（head 状态协议与设备注册）、ADR-0028（部署模式）、ADR-0029（账号与 E2EE 信任分离）、DP-019/023/025（相邻 DP）、DP-027/ADR-0030-0031（localhost 边界先例）

## 1. 问题与范围

团队域的协作模型是"成员提交 Proposal（含 Candidate Revision），审核者审批"。Proposal key 是审核者在该流程中的密码学凭证。DP-018 必须裁决：这个凭证**是什么**（信任定位）、**怎么到达审核者**（分发渠道）、**怎么失效**（撤销语义），以及与相邻 DP 的边界。

本 ADR 是纯设计切片：不实现团队 Proposal E2EE（DP-018 hard stop），不翻转正式 registry 的 THR/INV/ACC（候选文本见 §8，随未来实现合同落库），不改既有 ACC 证据。

## 2. 行业先例（调研 2026-09-12）

| 先例 | 采用的机制 | 对本设计的启示 |
| --- | --- | --- |
| MLS（RFC 9420/9750） | 凭证经认证服务注册（KeyPackage），私钥永不传输；成员移除走 Remove 提案 + commit，**epoch 前进带来前向安全**；凭证过期即可被移除 | 公钥注册走认证通道、私钥本地生成是成熟模式；内容层面的"撤销后不可读"由群密钥轮换（= 本项目 DP-025）承担，不由凭证层承担 |
| TUF | 离线根角色**签发委托**：根签名承认各角色公钥，撤销 = 根重签角色清单；私钥留在角色所有者处 | "分发"应定义为**对公钥的签名承认**，而非私钥传递；高权限材料离线/本地保存 |
| GitHub/GitLab 签名提交 | 签名证明作者身份，评审证明内容质量；**验收时验证并持久化验证状态**，否则密钥轮换/过期会改写历史 | 审批在"验收时"验证并持久化（记录所用注册表状态），事后撤销不重写已验收事实 |

## 3. 裁决一：信任定位——审批签名凭证，不是内容密钥

1. Proposal key 是**每个审核者自己的审批签名密钥对**（ECDSA P-256/SHA-256，与 head 设备签名同代际），私钥在审核者自己的已授权设备上本地生成、永不离开设备。
2. 它**不是**内容密钥：待审 Proposal 内容的加解密与读取权属于团队群密钥体系（DP-025 group epoch）。DP-018 只裁决审批凭证的注册、分发（承认）与撤销。
3. 它不改变既有信任根：head 签名权仍属 devices.json 注册设备；账号托管会话（ADR-0029）与审批凭证完全分域——登录账号不隐含审批权，审批凭证不隐含账号。
4. 与 head 设备的关系：审批凭证**绑定到审核者的某台已注册设备**（device-id 关联），但独立注册、独立撤销——撤销审批权不撤销设备，撤销设备不隐含撤销审批权（两者是独立登记项）。

## 4. 裁决二：分发渠道——既有设备批准链上的公钥签名承认

1. **分发 = 承认，不是传递**：审核者在其设备本地生成密钥对，把**公钥**（+指纹）经既有带外通道出示给域所有者（信任锚复用 devices.json 的批准方）；所有者设备用既有授权签名权把该公钥写入 **`proposal-reviewers.json`**——一个类似 `devices.json` 的显式注册表（每条目：reviewer 标识、公钥 spki、device-id 绑定、registered_at、单调序号），文件与 head 目录同域存放、同样只经签名更新。
2. **明确否决的替代方案**：(a) 类 Recovery File 的 bearer 私钥材料离线分发——私钥多手传递制造本项目一直避免的共享秘密面，且撤销无法回收已拷贝的私钥；(b) 服务器/托管层分发——违反 ADR-0029（托管层不进入 E2EE 信任根）与 ADR-0028 并行模式（设备本地优先、无强制服务器）。
3. 谁有承认权（注册权威）：v1 默认为**域所有者的已授权设备**（与设备注册同权威）；多人治理、法定人数、丢失恢复留给 **DP-019**（接口留白见 §7）。
4. 本设计在设备本地与自托管（ADR-0028 并行模式）下同构：注册表是域内文件，无需在线服务持有任何秘密。

## 5. 裁决三：撤销语义——前向失效 + 历史持久化，不冒充内容撤销

1. **撤销 = 签名注册表更新移除该公钥**（同注册权威），序号单调递增；验证方拒绝回滚的旧版注册表（复用 head 协议的防回滚形态）。
2. **前向失效**：撤销后，该审核者的签名对新 Proposal 一律无效——验证是失败关闭的（未注册/已撤销密钥的审批与未注册设备的 head 同型拒绝）。
3. **历史持久化**：Proposal 被验收时即验证审批签名并**持久化验收记录**（审批签名 + 当时注册表状态摘要，GitHub 验收时持久化先例）；事后撤销不重写已验收事实，也不使历史审批"变得从未有效"。
4. **不冒充内容撤销**：撤销审批凭证**不**声称使被撤审核者读不到后续待审内容——那需要 DP-025 的 epoch 前向安全轮换。这是本设计的显式边界（诚实边界 §9），不是缺陷豁免：实现合同必须把这条边界写进 UI 文案与文档，禁止"已撤销其全部访问权"类表述。
5. 审批凭证泄露的应急流程 = 撤销 + （内容层的善后依赖 DP-025 epoch 轮换）+ DP-019 兜底（治理恢复）。

## 6. 撤销测试计划（DP-018 close_artifact 的"revocation tests"；设计级，随实现合同落库执行）

| # | 场景 | 期望 |
| --- | --- | --- |
| RT-1 | 未注册公钥的审批签名 | 验收失败关闭，归一化拒绝码，无部分验收 |
| RT-2 | 已撤销密钥对新 Proposal 的审批 | 同 RT-1；撤销后的注册表序号更高，旧表不可回滚生效 |
| RT-3 | 注册表回滚（用旧序号签名表替换新表） | 防回滚检查拒绝，与 head 协议同型 |
| RT-4 | 注册表文件被篡改（签名破坏） | 拒绝；不得退化为"按未签名表继续" |
| RT-5 | 撤销后历史验收记录 | 已持久化的验收记录仍可验证为"验收时有效"；验收记录包含注册表状态摘要且匹配 |
| RT-6 | 撤销审核者尝试重新自注册（无承认权威签名） | 失败关闭；无任何自我承认路径 |
| RT-7 | 审批凭证与设备撤销独立 | 撤销审批凭证不删除设备注册；撤销设备不自动撤销审批凭证（两个登记项独立报错） |
| RT-8 | 私钥不出设备 | 注册流程任何产物中不含私钥材料（字节级扫描） |

## 7. 与相邻 DP 的接口留白

- **DP-019（治理恢复）**：注册权威全体丢失时的恢复流程（TUF 离线根式带外恢复）、法定人数、管理员紧急审批——全部留给 DP-019；本设计的注册权威默认是"域所有者的已授权设备"，DP-019 可扩展权威集合而不改注册表结构。
- **DP-025（group epoch）**：待审内容的密钥分发、成员加入/退出、撤销后的内容前向安全，全部由 group epoch 承担；`proposal-reviewers.json` 的成员集合是 epoch 成员规则的输入之一，但本设计不定义 epoch 机制。
- **DP-023（额度/风险）**：Proposal 数量/大小阈值与审批流解耦；本设计不引入任何阈值。

## 8. 候选 registry delta（设计候选，随实现合同落库；编号届时按尾号连续分配）

- 候选威胁：**PRO-THR-01** 注册表篡改/回滚；**PRO-THR-02** 未注册/已撤销密钥的审批被接受；**PRO-THR-03** 私钥材料经注册流程泄露；**PRO-THR-04** 撤销被表述为内容撤销（虚假声明）。
- 候选不变式：**PRO-INV-01** 审批有效性 = 注册表中未撤销公钥的合法签名 + 验收时持久化；**PRO-INV-02** 注册表更新单调序号 + 授权签名；**PRO-INV-03** 私钥永不进入注册流程产物；**PRO-INV-04** 撤销不重写历史验收记录。
- 候选 ACC：注册表防回滚负例、未注册/撤销审批负例、验收持久化往返、注册产物私钥字节扫描。

## 9. 诚实边界

1. 撤销审批凭证 ≠ 撤销内容访问权（内容层依赖 DP-025，未实现前该边界必须显式声明）。
2. 团队 Proposal 全流程（提交、待审、审批、验收）属于未来实现合同；本 ADR 关闭不授权任何实现。
3. 单审批权威（v1 默认）不是治理模型：多人权威、法定人数、恢复是 DP-019 的课题。

## 10. 自检记录（开发者委托的多轮多角度检查，2026-09-12）

**第一轮（起草后四视角）**

- **管理者视角**：审批权登记有审计轨迹吗？→ 注册表是签名+单调序号文件，配合既有 history journal 形态可追加审计（实现合同落库）；多人团队规模 → 注册表支持 N 个条目、device-id 绑定天然支持一人多设备。缺口：注册/撤销事件的时间线呈现——记入实现合同要求（§6 RT-5 的持久化记录即审计基础）。**修订：在 §4.1 明确"每次注册/撤销必须产生可追加审计记录"。
- **用户（审核者）视角**：拿到审批权的流程是什么？→ 本地生成 → 出示公钥指纹 → 所有者批准 → 下次同步生效；无需文件搬运、无需账号。被撤销的体验 → 下次提交审批时得到明确归一化错误。缺口：公钥指纹出示方式（文本/二维码）属于实现合同 UI 课题，不影响本设计。**修订：无（记录为实现课题）。
- **部署视角**：自托管/本地两种模式是否同构？→ 注册表是域内文件，与 devices.json 同生命周期，无服务器秘密；迁移（未来 DP-022）时注册表随域状态走。缺口：注册表与 head 目录的物理布局（同目录/子目录）留给实现合同，须遵守 ADR-0021/0009 路径纪律。**修订：§4.1 已注明"与 head 目录同域存放"。
- **安全视角**：最大风险 = 撤销被误读为内容撤销（§5.4 已显式边界）+ 注册权威单点（§9.3 显式留白 DP-019）；私钥传递面已消除（§4.2 否决 bearer 方案）；防回滚复用已验证的 head 形态。**修订：无新增。

**第二轮（修订后复核）**

- 复核 hard stop：本切片零实现、零 registry THR/INV/ACC 翻转 ✓；四条裁决（§3/§4/§5）相互一致，无与 ADR-0026/0028/0029 冲突项 ✓；RT-1..RT-8 覆盖撤销语义各分支且与候选 ACC 对齐 ✓；DP-019/023/025 接口留白无重叠声明 ✓。结论：可关闭 DP-018。

## 11. 后果与停止点

- DP-018 关闭（closure_adr = 本 ADR）；团队 Proposal E2EE 的实现仍被 hard stop 阻止，须待 DP-025/019 相关合同与实现切片另行授权。
- 本设计不改变 head 协议、设备注册、账号边界、localhost 边界的任何既有裁决。
- 开发者若否决任一被采纳的裁决（§3/§4/§5），DP-018 重开为 deferred，相关文档同轮回滚。
