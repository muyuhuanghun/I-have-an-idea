# ADR-0033：P1-beta 团队 group epoch、成员加入退出与旧代际读取边界设计（DP-025）

- 状态：**已接受（2026-09-12）——开发者委托裁决（"开工 DP-025"），本 ADR 采纳推荐选项并经四视角两轮自检；任何裁决可被开发者事后否决，否决即回滚关闭状态**
- 日期：2026-09-12
- 决策者：开发者（OWNER-SECURITY 归属；本轮委托按推荐路径裁决）
- 阶段：P1-beta team key lifecycle（DP-025 关闭切片，纯设计，不含实现）
- 相关文档：DP-025（registry）、DP-018/ADR-0032（proposal-reviewers 注册表，本设计的成员输入之一）、ADR-0026/0027（head 状态协议与防回滚形态）、ADR-0028（部署模式）、ADR-0029（账号与 E2EE 信任分离）、DP-019（治理恢复）、DP-023（额度）

## 1. 问题与范围

团队域的内容密钥生命周期：什么时候换密钥（epoch 触发）、新成员能读什么（加入起点）、退出/被撤销成员读不到什么（旧代际读取边界）。DP-018 已裁决审批凭证层并把内容层显式留白给本 ADR；本 ADR 关闭后，P1-beta 设计族（DP-018 + DP-025）齐备，治理恢复（DP-019）是最后一块设计。

本 ADR 是纯设计切片：不实现真实团队成员加密、撤销或任何 epoch 机制（hard stop），不翻转正式 registry 的 THR/INV/ACC（候选见 §8），不产生运行证据——"join/revoke/old-epoch acceptance evidence" 在本切片落为**验收证据计划**（§6），实际证据随实现合同产生。

## 2. 行业先例（调研 2026-09-12）

| 先例 | 机制 | 对本设计的启示 |
| --- | --- | --- |
| MLS（RFC 9420/9750，上轮已调研） | 每次成员变更 commit 都推进 epoch；移除走 Remove 提案；epoch 前进 = 前向安全 | 成员变更必推代际、变更即前向安全是标准形态 |
| Signal Sender Keys | 退出成员保留**旧消息的链知识**（已见的历史读得了）但读不了新消息；重新加入需重新分发 | "退出者保留已获得的知识"是被广泛接受的诚实边界，不是缺陷 |
| WhatsApp 群邀请 | 新成员默认读不到加入前历史；"加密共享聊天记录"是邀请时的**显式独立动作** | 历史补发必须是显式能力而非默认；v1 不做，留作未来可选项 |

## 3. 裁决一：epoch 触发——成员集合变更必推代际，v1 不做批量轮换

1. 以下事件各自**必须**推进 epoch：成员加入、成员主动退出、成员被移除、审批凭证撤销导致内容组成员变化（联动 ADR-0032 的 `proposal-reviewers.json`）、成员名下全部设备被撤销（ADR-0026 设备注册语义联动）。
2. epoch 推进 = 生成新的群内容密钥体系并**从活跃成员设备上擦除上一代内容密钥**（密钥擦除是前向安全的前提，实现合同必须定义擦除的可验证语义）。
3. v1 不做延迟/批量轮换（省性能的"攒一批变更再换钥"会拉长被移除者读新内容的窗口，v1 拒绝该优化；若未来引入，须另立裁决并量化窗口）。
4. epoch 序号单调递增、防回滚，复用 ADR-0026/0027 head 协议的签名指针 + 序号形态；并发成员变更必须串行化（同一时刻只有一个 epoch 推进被接受）。

## 4. 裁决二：新成员起点——只见未来，历史补发是显式独立能力

1. 新加入成员从其加入的 epoch 起获得内容密钥：**只能读加入之后的内容**，加入之前的密文对其密码学不可读（Signal 默认形态）。
2. "把历史共享给新成员"（WhatsApp 式加密补发）是显式的独立能力，v1 **不做**；若未来引入，必须是被审查的独立动作（成本：把历史重加密给新成员 = 重新分配旧内容密钥，等价于放弃对这部分历史的前向安全），不得作为默认行为混入。
3. 加入起点之上不区分"新成员/老成员"权限层级——内容级权限（谁能看哪类 Proposal）是 DP-019/未来治理模型的课题，本设计只定义全体活跃成员一致的群内容密钥。

## 5. 裁决三：旧代际读取边界——三级诚实声明，v1 不做旧密文重加密

退出/被撤销成员的读取能力按三级如实划分，任何文档与 UI **禁止**跨级表述：

| 层级 | 内容 | 退出/被撤销成员 | 性质 |
| --- | --- | --- | --- |
| L1 已下载历史 | 此前已同步到其设备的明文/密文 | 保留读取能力 | 事实边界（hard stop 明示不可声称失去） |
| L2 共享存储中未下载的旧 epoch 密文 | 仍留在共享 ObjectStore 的历史密文对象 | **密码学上仍可解**（其曾持有该 epoch 密钥）；v1 缓解 = 传输/存储访问层在成员移除后停止向其提供旧代际对象的获取（网络边界缓解，非密码学缓解，必须如实区分） | 显式接受的限制 |
| L3 移除 epoch 之后的一切内容 | 新 epoch 起产生的密文 | 密码学不可读（新密钥不发给它 + 旧密钥已擦除） | 前向安全承诺 |

1. **v1 不做旧密文重加密**（把 L2 变成密码学不可读需要重加密全部历史或每 epoch 密钥失效机制，成本与复杂度在 v1 不成比例）；"密码学级 L2 失效"列为未来可选能力，若引入须另立裁决。
2. 传输层缓解（L2 的访问停止）只在存在共享传输的部署形态适用（ADR-0024/0028 的 HTTP/自托管路径）；纯设备本地单用户域不涉及团队 epoch。网络缓解与密码学缓解的措辞必须在实现合同的 UI/文档文案中区分。
3. 成员移除的完整善后 = L3 前向安全（本设计承诺）+ L2 访问停止（部署形态承诺）+ L1 如实告知（产品文案承诺）+ DP-019 治理兜底。

## 6. 验收证据计划（DP-025 close_artifact 的"join/revoke/old-epoch acceptance evidence"；设计级，随实现合同落库执行）

| # | 场景 | 期望 |
| --- | --- | --- |
| ET-1 | 成员加入后尝试读取加入前 epoch 密文 | 密码学不可读（无该 epoch 密钥），如实呈现为不可读而非错误 |
| ET-2 | 成员加入后读取加入后内容 | 正常可读 |
| ET-3 | 成员被移除后尝试读取移除后 epoch 内容 | 密码学不可读；被移除者设备上旧 epoch 密钥已按擦除语义消失 |
| ET-4 | 成员被移除后本机已下载历史 | 如实保留（产品文档/UI 不得声称其丢失）；本用例验证"历史仍可读"是被文档化行为而非实现漏洞 |
| ET-5 | 共享存储对已移除成员的旧代际对象获取 | 传输/存储访问层拒绝（适用部署形态下）；措辞区分网络缓解 |
| ET-6 | epoch 状态注册表回滚/篡改 | 防回滚与签名验证拒绝（与 head 协议同型失败关闭） |
| ET-7 | 并发成员变更 | 串行化：恰好一个 epoch 推进被接受，其余被拒或合并后单次推进 |
| ET-8 | `proposal-reviewers.json`（ADR-0032）成员集合变化 | 正确联动触发 epoch 推进；无成员集合变化时不推进（防无谓轮换与重放式推进） |
| ET-9 | epoch 推进后的密钥擦除 | 活跃成员设备上可验证旧内容密钥已不存在（字节/内存扫描级断言） |

## 7. 与相邻 DP 的接口留白

- **DP-018/ADR-0032**：`proposal-reviewers.json` 的成员集合是本设计 epoch 成员输入之一（ET-8）；审批凭证撤销联动内容组移除。
- **DP-019（治理恢复）**：注册权威全体丢失后的恢复 = 重建 group state 与成员集合（epoch 序号延续、不重置）；恢复流程是最后一块 P1-beta 设计。
- **DP-023（额度/风险）**：成员数量/Proposal 规模阈值与本设计解耦。
- **ADR-0028/0024**：L2 传输层缓解依赖共享传输形态的访问控制；设备本地单用户域不涉及本设计。

## 8. 候选 registry delta（设计候选，随实现合同落库；编号届时按尾号连续分配）

- 候选威胁：**GRP-THR-01** epoch 状态注册表篡改/回滚；**GRP-THR-02** 被移除成员仍能获取新 epoch 内容密钥；**GRP-THR-03** 密钥擦除不可验证（声称擦除实际残留）；**GRP-THR-04** 把 L2 网络缓解表述为密码学撤销（虚假声明）；**GRP-THR-05** 并发变更导致双_epoch 分叉。
- 候选不变式：**GRP-INV-01** 成员集合变更必推 epoch 且序号单调；**GRP-INV-02** 新成员仅从加入 epoch 起可读；**GRP-INV-03** 被移除成员对新内容密码学不可读；**GRP-INV-04** 旧内容密钥在推进后按可验证语义擦除；**GRP-INV-05** L1/L2/L3 边界的对外表述不得越级。
- 候选 ACC：ET-1..9 对应的实机正负例。

## 9. 诚实边界

1. L2 的网络缓解不是密码学撤销——拥有旧密钥与旧密文副本的退出者在共享存储之外仍可自行解密，本设计不声称否则。
2. v1 无历史补发能力；引入即放弃对应历史的前向安全，须独立裁决。
3. 团队内容的实际加解密流程（成员如何用 epoch 密钥封装 Proposal/快照）属于实现合同；本 ADR 关闭不授权任何实现。

## 10. 自检记录（开发者委托的多轮多角度检查，2026-09-12）

**第一轮（起草后四视角）**

- **管理者视角**：成员生命周期操作有审计锚吗？→ epoch 状态注册表是签名+单调序号文件，每次推进可追加审计记录（同 ADR-0032 §10 修订要求）；成员名单变更频率决定轮换开销 → v1 每变更必换，团队高频变更场景的开销记为实现合同的性能课题。**修订：§3.3 补充"高频变更的开销量化留实现合同"。
- **用户（成员）视角**：加入体验 = 所有者批准 + 从当期起读；退出体验 = 自己的历史保留、之后内容不可读且文档如实说明——三张边界表（§5）必须进用户文档。缺口：被移除时的即时通知属产品 UI 课题。**修订：无（记录为实现课题）。
- **部署视角**：group state 放哪？→ 域内签名文件（与 devices.json/proposal-reviewers.json 同生命周期、head 目录同域），设备本地单用户域不涉及；自托管形态下 L2 的访问控制在传输层（ADR-0024 语义）实现。缺口：多设备同一成员的"名下全部设备撤销→成员移除"联动已在 §3.1 覆盖。**修订：§5.2 已注明适用形态。
- **安全视角**：最大虚假声明风险 = L2 被表述成密码学撤销（GRP-THR-04/INV-05 显式防守）；密钥擦除必须可验证（ET-9）；并发分叉由串行化防守（ET-7）。**修订：无新增。

**第二轮（修订后复核）**

- hard stop 遵守：零实现、零 registry 翻转 ✓；三级边界与 DP-018 留白、hard stop 措辞（"不得声称退出成员失去已下载历史"）逐字对齐 ✓；ET-1..9 覆盖三条裁决各分支 ✓；与 DP-018/019/023/ADR-0026/0028/0029 无冲突声明 ✓。结论：可关闭 DP-025。

## 11. 后果与停止点

- DP-025 关闭（closure_adr = 本 ADR）；真实团队成员加密、撤销、epoch 机制的实现仍被 hard stop 阻止，须待实现合同（建议与 DP-018 的 proposal 注册表合并为 P1-beta 实现阶段切片）另获授权。
- 本设计不改变 head 协议、设备注册、账号边界、localhost 边界的任何既有裁决。
- 开发者若否决任一被采纳的裁决（§3/§4/§5），DP-025 重开为 deferred，相关文档同轮回滚。
