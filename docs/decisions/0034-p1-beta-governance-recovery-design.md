# ADR-0034：P1-beta 紧急治理恢复的精确范围与签名建议权限设计（DP-019）

- 状态：**已接受（2026-09-12）——开发者委托裁决（"开工 DP-019"），本 ADR 采纳推荐选项并经四视角两轮自检；任何裁决可被开发者事后否决，否决即回滚关闭状态**
- 日期：2026-09-12
- 决策者：开发者（OWNER-PRODUCT 归属，安全面 OWNER-SECURITY 复核；本轮委托按推荐路径裁决）
- 阶段：P1-beta/P1-release governance（DP-019 关闭切片，纯设计，不含实现）
- 相关文档：DP-019（registry）、ADR-0032（proposal-reviewers 注册权威）、ADR-0033（group epoch 序号延续）、ADR-0005/0006（Recovery File 秘密模型与分域先例）、ADR-0026/0027（设备注册与 head 协议）、ADR-0029（账号与 E2EE 信任分离）、DP-023（额度，解耦）

## 1. 问题与范围

注册权威（承认设备/审核者/成员集合的签名权）可能整体不可用：所有者授权设备全部毁损、泄露应急、人员变动。DP-019 必须裁决：**紧急恢复的精确范围**（能恢复什么、永远不能做什么）与**签名建议权限**（紧急场景下管理员/建议者的权限边界）。hard stop 已定调：不得赋予管理员绕过正常审核的治理恢复权限——本设计将其落为"建议与授权分离"的结构性规则（§4）。

本 ADR 是纯设计切片：不实现恢复流程、不翻转正式 registry 的 THR/INV/ACC（候选见 §8），不产生运行证据——"role/approval matrix" 在本切片落为设计冻结矩阵（§6），实现与证据随实现合同另行授权。

## 2. 行业先例（调研 2026-09-12）

| 先例 | 机制 | 对本设计的启示 |
| --- | --- | --- |
| TUF（上轮已调研） | 离线根角色是唯一能重建其他角色权威的信任锚；根签名承认 = 分发的本质 | 恢复 = 用离线材料重建"承认权"，不是重写登记历史 |
| SLIP-39 / Shamir 份额与社会化恢复 | k-of-n 阈值份额离线分存，消除单点保存；重组须在安全环境 | 阈值份额化是有价值的未来选项；v1 与 Recovery File 纪律对齐取单份离线，份额化留作裁决 |
| MetaMask/硬件钱包恢复纪律 | 恢复短语离线保存、永不在线、泄露不可远程吊销 | 离线 bearer 材料的诚实边界：泄露无法远程撤销，纪律与应急重建是唯一缓解 |

## 3. 裁决一：信任锚——治理恢复材料，与 Recovery File 分域

1. 团队域创建时生成**治理恢复材料**：离线保存的 bearer 材料（与 ADR-0005/0006 Recovery File 同型的地位与保存纪律——离线、永不在线传输、泄露不可远程吊销）。
2. **分域是硬边界**：治理恢复材料只恢复**登记权威**（各注册表的承认签名权），与 Recovery File（域密钥/内容恢复）互不重叠——任何一方泄露不授予另一方的能力（GOV-INV-03）。它也绝不授予任何内容访问（ADR-0029 信任分离的延续）。
3. v1 取单份离线材料（与 Recovery File 纪律一致）；Shamir k-of-n 份额化是未来可选裁决（消除单点保存 vs 份额泄露面扩大，须独立权衡），不得默认混入。
4. 材料可重复使用（权威可能多次转移），每次使用产生不可篡改的恢复事件审计记录；泄露材料的诚实边界见 §9。

## 4. 裁决二：精确范围与建议-授权分离

### 4.1 恢复"能"做什么（且仅此）

1. 在**安全环境**验证治理恢复材料与域的绑定后，承认一台新的所有者设备（显式设备注册，复用 ADR-0026 语义——承认权来自恢复材料而非凭空产生）；
2. 由此重建各注册表（`devices.json`、`proposal-reviewers.json`、group state）的签名权威；被恢复取代的旧权威设备登记标记 `superseded`（不删除——历史持久化，同 ADR-0032 §5.3）；
3. epoch 序号**延续不重置**（ADR-0033 §7）；成员资格不因恢复而改变（成员资格是事实，恢复只重建设施）；
4. 恢复事件本身追加进审计记录。

### 4.2 恢复永远"不能"做什么（结构性禁令）

1. **不签发/验收 Proposal 内容**——审批验收永远是审核者自己的审批签名权（ADR-0032），恢复材料与管理员都不持有该权；
2. **不读取任何成员内容**——不授予内容密钥、不进入群 epoch 密钥体系（ADR-0033）；
3. **不重写/删除任何历史登记与审计记录**——恢复只重建设施，不重写事实；
4. **不绕过设备注册语义**——新设备仍走显式注册，恢复材料只是承认权的来源。

### 4.3 签名建议权限：建议与授权分离

紧急场景下的"管理员"（v1 可不设置该角色）**只有建议权**：发起恢复请求、提名应恢复的设备/成员清单、请求传输层紧急止血（ADR-0033 L2 访问停止）。建议不产生任何登记效力——一切密码学承认必须由治理恢复材料或幸存权威设备完成。这把 hard stop（"不得赋予管理员绕过正常审核的治理恢复权限"）落为结构性规则：**管理员在任何矩阵格子里的权限都不含"承认签名"与"内容访问"**（矩阵见 §6，GOV-INV-01）。

## 5. 恢复流程（离线 TUF 根式，v1 冻结为六步）

1. 安全环境导入治理恢复材料；
2. 材料验证（与域绑定校验 + **dry-run 校验**：不执行恢复即可验证材料有效性，供定期演练）；
3. 承认新所有者设备（显式注册）；
4. 旧权威设备登记标 `superseded`（不删除）；
5. 各注册表签名权威重建；epoch 序号延续；成员集合不变；
6. 恢复事件追加审计记录。

## 6. 角色-审批矩阵（v1 设计冻结；实现合同按表落库）

## 8. 候选 registry delta（设计候选，随实现合同落库；编号届时按尾号连续分配）

- 候选威胁：**GOV-THR-01** 治理恢复材料泄露即登记权威失守（离线纪律防守，泄露不可远程吊销）；**GOV-THR-02** 管理员建议被实现为授权（建议冒充承认）；**GOV-THR-03** 恢复被实现为历史重写；**GOV-THR-04** 恢复被表述为内容访问恢复；**GOV-THR-05** 恢复材料与 Recovery File 混域。
- 候选不变式：**GOV-INV-01** 建议与授权分离（任何建议角色不持承认签名/内容访问）；**GOV-INV-02** 恢复只重建设施不重写事实；**GOV-INV-03** 治理材料与内容密钥/Recovery File 严格分域；**GOV-INV-04** epoch 序号只延续不重置；**GOV-INV-05** 恢复事件必须可审计。
- 候选 ACC：GR-1..10 对应实机正负例。

## 9. 诚实边界

1. 治理恢复材料是单点全能的**登记权威**凭证：泄露在密码学上不可远程吊销（离线 bearer 先例）；唯一缓解 = 幸存权威尽快重建承认 + 恢复事件审计 + 离线保存纪律。**治理材料轮换**（re-issuance）列为未来裁决。
2. 恢复不等于内容恢复：内容密钥的丢失恢复仍走 Recovery File 体系（分域）；治理恢复后成员各自的内容可读性不变。
3. 单所有者 + 单份材料是 v1 现实选择：法定人数/份额化/多人治理全部留给未来裁决；在引入前，文档不得暗示存在"多人制衡"。
4. 恢复流程的实现属于实现合同；本 ADR 关闭不授权任何实现。

## 10. 自检记录（开发者委托的多轮多角度检查，2026-09-12）

**第一轮（起草后四视角）**

- **管理者视角**：恢复多久能演练一次？→ dry-run 校验（流程步骤 2）使定期演练无需真实恢复；恢复事件审计满足合规追溯。缺口：恢复演练的频率建议属运营文档。**修订：§5.2 补 dry-run。
- **用户（所有者）视角**：v1 单人场景 = 自己持有材料 + 自己设备即权威，管理员角色可空——无强制角色负担；丢失场景路径清晰（材料 → 新设备）。缺口：材料离线保存的介质建议属运营文档。**修订：§6 注明管理员列可空。
- **部署视角**：设备本地与自托管模式同构（材料离线、流程本地执行）；恢复后 ADR-0033 L2 传输缓解对新权威设备自然可用；自托管服务不持有治理材料。**修订：无。
- **安全视角**：最大风险 = 材料单点（§9.1 显式 + 泄露不可吊销的诚实声明）；建议-授权分离是结构性而非流程性防守（矩阵逐格可测，GR-5）；分域扫描（GR-9）防实现混域。**修订：§9 补充"材料轮换列未来裁决"。

**第二轮（修订后复核）**

- hard stop 逐字对齐：矩阵中管理员无任何"绕过正常审核"路径（验收行永久禁止 + GR-5 逐格断言）✓；与 ADR-0032/0033 接口（注册表结构不变、epoch 延续、superseded 语义）一致 ✓；GR-1..10 覆盖三条裁决与矩阵各列 ✓；分域与诚实边界（§9）无越级声明 ✓。结论：可关闭 DP-019。

## 11. 后果与停止点

- DP-019 关闭（closure_adr = 本 ADR）；P1-beta 设计族（DP-018/025/019）至此齐备，治理恢复的实现与 DP-018/025 的实现同属团队协议实现阶段，另获授权。
- 本设计不改变 head 协议、设备注册语义、账号边界、localhost 边界的任何既有裁决；恢复材料不触碰内容密钥与 Recovery File 体系。
- 开发者若否决任一被采纳的裁决（§3/§4/§5/§6），DP-019 重开为 deferred，相关文档同轮回滚。
