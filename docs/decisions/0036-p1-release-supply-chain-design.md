# ADR-0036：P1-release 签名更新、可验证构建与供应链边界设计（DP-020）

- 状态：**已接受（2026-09-12）——开发者委托裁决（"继续 P1-release 设计族"），采纳推荐选项并经四视角两轮自检；可事后否决，否决即回滚关闭状态**
- 日期：2026-09-12
- 决策者：开发者（OWNER-SECURITY 归属；委托按推荐路径裁决）
- 阶段：生产发布前（DP-020 关闭切片，纯设计；"reproducible-build/signing evidence" 落为验收证据计划，实现与正式证据随发布工程切片另授权）
- 相关文档：DP-020、THR-05（供应链攻击，本 ADR 关闭后改判）、ADR-0013（crypto suite）、ADR-0035（build-meta/bundle_sha256 先例）、TUF/可复现构建调研（2026-09-12）

## 1. 问题与范围

产品进入发布形态前必须回答：用户如何信任一个更新包（签名更新）、构建产物是否可复现（可验证构建）、供应链的信任边界画在哪里（依赖/工具链/发布链）。hard stop 关联：关闭前 THR-05 供应链攻击保持 out-of-scope；本设计关闭后 THR-05 改判为"更新链已缓解，开发端残留风险如实声明"。

## 2. 行业先例（调研 2026-09-12）

| 先例 | 机制 | 启示 |
| --- | --- | --- |
| TUF（前轮已调研） | 离线根密钥签名角色委托；更新元数据带过期与回滚防御 | 更新信任 = 离线发布密钥 + 带版本/过期的签名清单 |
| SLSA/sigstore | 构建出处（provenance）分级；keyless 签名 | 可验证构建按等级推进，v1 取"确定性工具链 + 双次构建哈希一致"级别 |
| 本项目 build-meta 先例（ADR-0035 引用） | bundle_sha256 + source_commit 绑定 | 已有产物完整性绑定的实现基础，发布层只需扩展 |

## 3. 裁决一：更新签名体系——离线发布密钥 + 版本化签名清单

1. 每个发布物（CLI 包、插件包）发布时生成**签名更新清单**：`{ channel, version, source_commit, toolchain: {node, pnpm, esbuild 版本}, artifacts: [{path, sha256}], released_at, signature }`，清单整体由**离线发布密钥**（ECDSA P-256，与运行时密钥分域，离线保管同 Recovery/治理材料纪律）签名。
2. 客户端/用户侧验证顺序：发布密钥验证清单签名 → 版本不得低于当前（防回滚）→ 逐产物 sha256 比对 → 全过才可安装/应用。任何一步失败关闭，无旁路。
3. 更新通道 v1 只有 stable 一条；预发布通道（beta）留作未来裁决，清单字段预留 `channel`。

## 4. 裁决二：可验证构建——确定性工具链 + 双次构建一致

1. 构建确定性三要素冻结：Node 版本（package.json `engines` + `.nvmrc`）、依赖锁（pnpm-lock.yaml 完整性，CI 禁止 `--frozen-lockfile` 之外的安装模式）、打包器版本（esbuild 精确版本已在 lock）。
2. 可验证构建证据 = 同一 commit 在干净环境**两次独立构建**，全部发布产物 sha256 一致（esbuild 输出的确定性在本仓库产物范围内验证；JS 产物已知非字节确定的字段——若有——必须在清单中显式列出豁免并说明）。
3. 发布物延续既有 `build-meta.json`（source_commit + bundle_sha256）并扩展为完整工具链清单；运行时 bundle 完整性校验（现有 `#loadBuildMeta` 机制）自动覆盖发布物。

## 5. 裁决三：供应链边界——更新链已缓解，开发端残留如实声明

1. **已缓解（本设计关闭后 THR-05 改判依据）**：更新包伪造/替换（签名清单）、更新回滚（版本下限）、构建产物被调包（可复现构建 + bundle 校验）、依赖静默投毒进入发布物（锁定 + 构建产物哈希使其可检出）。
2. **残留风险（如实声明，不声称缓解）**：开发机本身被入侵（签名密钥离线降低但不消除）；上游依赖的深层次恶意行为若不改变产物字节则不可检出；用户环境的安装通道（操作系统下载/浏览器）不在本项目边界。
3. 第三方 Action/CI 的信任：v1 发布以本地构建为准（开发者机器 + 离线密钥），CI 自动发布留作未来裁决。

## 6. 验收证据计划（设计级，随发布工程切片落库执行）

| # | 场景 | 期望 |
| --- | --- | --- |
| SB-1 | 篡改发布物任一字节后走验证流程 | 清单哈希比对失败关闭 |
| SB-2 | 错误发布密钥/未签名清单 | 验证失败关闭，无部分安装 |
| SB-3 | 旧版本清单（版本回滚） | 版本下限拒绝 |
| SB-4 | 同 commit 双次独立构建 | 发布产物 sha256 全一致（豁免清单外） |
| SB-5 | 运行时 bundle 完整性 | 与 build-meta 不符即拒绝运行（现有机制回归） |
| SB-6 | 依赖完整性 | lockfile 哈希与安装后树一致，非冻结安装被拒 |

## 7. 候选 registry delta（随发布工程切片落库）

候选威胁 **REL-THR-01** 更新包伪造/回滚、**REL-THR-02** 构建产物被调包、**REL-THR-03** 依赖投毒进入发布物；候选不变式 **REL-INV-01** 更新必须通过离线密钥签名清单验证、**REL-INV-02** 版本单调、**REL-INV-03** 发布产物哈希闭环、**REL-INV-04** 构建确定性可双次验证；候选 ACC 对应 SB-1..6。

## 8. 诚实边界

1. 开发端供应链（开发者机器、上游依赖深层恶意）不在本设计的缓解承诺内。
2. 可验证构建 v1 承诺为"双次构建一致"级别，不声称完整 SLSA 等级或 hermetic CI。
3. 实现与正式证据随发布工程切片另授权；本 ADR 关闭不产出任何代码。

## 9. 自检记录（四视角两轮，2026-09-12）

**第一轮**：管理者——发布密钥离线纪律与 Recovery/治理材料同级（分域保管清单并入运营文档，修订：§3.1 注明）；用户——验证流程对用户可见形式（安装前校验输出）留实现合同；部署——本地构建 vs CI 构建的取舍已裁决（v1 本地，§5.3）；安全——THR-05 改判措辞必须限定"更新链"，§5.2 残留清单即改判边界。**第二轮**：hard stop 对齐（THR-05 改判以本关闭为前提 ✓）；六条证据覆盖三裁决 ✓；无与既有 ADR 冲突 ✓。结论：可关闭 DP-020。
