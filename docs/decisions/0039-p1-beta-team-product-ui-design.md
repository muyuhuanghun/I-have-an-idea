# ADR-0039：P1-beta 团队产品化 UI 设计（协议层产品接线切片）

- 状态：**已接受（2026-09-12）——开发者委托裁决（"团队产品化 UI"），采纳推荐选项并经四视角两轮自检；可事后否决**
- 上游：ADR-0032/0033/0034（设计）、ADR-0035（T1 合同 §6.4 预留的本切片）、T2 协议层（`d79b45f`）
- 阶段：P1-beta 产品接线（设计 + 实现同切片；T3 式正式证据不适用——本切片为产品 UI，无新 ACC）

## 1. 裁决

1. **承载面 = Obsidian 插件**：新增"团队"可停靠面板（复用既有 dockable view 模式）+ 设置页团队域配置（**团队域状态目录**绝对路径 + 本设备身份）。CLI 不加团队 UI（协议层已够）；**console 保持严格只读**（WEB-INV-02 已关闭证据，团队审批是写操作，绝不进 console）。
2. **共享形态**：团队域状态目录（T2 登记物所在目录）由用户的同步基础设施负责多机分发（与 ADR-0028 并行模式一致——产品不做自动同步）。单机多角色（所有者+审核者不同 Vault profile 指同一目录）即可用。
3. **提案内容层（T2 缺失的内容侧，最小新增）**：提案 = `{proposal_id, epoch, author_device_id, created_at, title, content}` 经当期 epoch CEK 的 AES-256-GCM 加密对象，存团队域状态目录 `proposals/` 子目录（一提案一文件，文件名 = proposal_id）；内容含元数据整体加密（标题不泄露）。列表 = 枚举 + 逐个解封（活跃成员有权读全部提案——ADR-0033 群内容语义内）。
4. **审批与验收**：审批 = ADR-0032 审批签名（绑定注册表状态哈希）追加进提案文件（文件内含历次审批记录，整体重加密）；验收语义 v1 = 提案标记"已获所需审批"（所需审批数 v1 = 1，即单审核者签认；治理矩阵多人数为 ADR-0034 未来裁决），**不做自动内容合并/应用**——验收后的处置是人的动作。
5. **密钥边界**：成员内容 DH 私钥存本机 localStorage（设备绑定先例），不入 data.json（防同步外泄）；epoch CEK 经 T2 unwrap 进内存，不持久化。
6. **无新 ACC**：本切片是产品 UI 接线，复用 T2 协议层证据（ACC-50..58）与既有插件测试纪律；安全结论不变式由底层承载。

## 2. 验收（切片测试）

插件测试：提案提交→加密落盘→列表解封→审批签名追加→再读取含审批（往返）；非成员设备解封失败关闭。实机 Obsidian：面板三段式可用。

## 3. 诚实边界

1. v1 单审核者签认 + 无自动处置；多人数审批/提案内容类型扩展留未来裁决。
2. 共享目录的多机一致性由用户同步设施负责；产品不处理同步冲突（冲突文件如实显示为不可读）。
3. 本切片无新正式证据；协议安全结论引用 T3（b58443e）。

## 4. 自检记录（四视角两轮）

管理者：提案索引整体加密防元数据泄露 ✓；审批审计在提案文件内 ✓。用户：提交/审批各一键；非审核者不见审批按钮 ✓。部署：共享目录 = 任意同步盘/网络盘可用；团队域目录未配置时面板如实显示未配置 ✓。安全：CEK 不持久化、DH 私钥限 localStorage、console 只读不动、加密对象 AAD 绑定提案 ID ✓。第二轮：与 ADR-0033 L 层级/ADR-0034 矩阵/WEB-INV-02 无冲突 ✓。结论：可实现。
